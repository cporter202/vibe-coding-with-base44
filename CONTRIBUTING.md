# Contributing

Contributions that make this guide more accurate, beginner-friendly, and useful are welcome.

## Good contributions

- Correct a stale UI label, limit, or plan requirement with an official source
- Add a reproducible troubleshooting case
- Improve a prompt by adding scope, permissions, edge cases, or tests
- Add or improve a starter kit with a version-one boundary, permission matrix,
  build order, and cross-user test
- Fix unclear instructions, broken links, or accessibility issues
- Add a small build-along that teaches a distinct pattern

## Before opening a pull request

1. Use Base44's official documentation as the source for product claims.
2. Avoid publishing private data, API keys, account IDs, or customer information.
3. Mark time-sensitive facts with a review date.
4. Keep promotional language out of instructional sections.
5. Put affiliate links only where the financial relationship is clearly disclosed.
6. Verify every relative link you touched.
7. Read the change as a beginner who does not know developer jargon.

## Style

- Say **Base44**, not Base 44 or base44 in prose.
- Prefer short sentences and observable outcomes.
- Define a technical term the first time it appears.
- Use fenced `text` blocks for Base44 prompts.
- Never claim a generated change is secure or tested without describing the checks.
- Link to the most relevant official page, not just the documentation home.

## Issues

For an inaccurate claim, include:

- The page and section
- What is incorrect
- A link to the current official source
- The date you verified it

Do not post account-specific problems or secrets in a public issue. Use Base44's support channels for private account or billing matters.
